RK3506 / ROS 2 SDK

RK3506 Mobile Base ROS 2 SDK

ROS 2 integration for the RK3506 Helishi two-swerve mobile robot controller. The SDK runs on the upper computer and communicates with the standalone RK3506 controller over UDP.

The C++ package is rk3506_driver. Controller firmware remains in the separate rk3506-can-interface-cpp repository. See validation for executed checks and outstanding physical acceptance.

Supported platforms

ROS 2 distributionOperating systemArchitectures
HumbleUbuntu 22.04ARM64, x86_64
JazzyUbuntu 24.04ARM64, x86_64

All four combinations passed build and integration checks. ARM64 checks ran natively in Docker; x86_64 checks used emulation. Physical robot acceptance remains outstanding.

Requirements

  • An upper computer with the appropriate ROS 2 installation, a C++17 compiler, colcon and configured rosdep.

  • Network access to the controller's UDP ports: 5003 for base commands/status, 5001 for battery and 5002 for digital inputs. Allow the corresponding UDP replies to the upper computer.

  • The companion controller access/handoff update described in controller integration.

Configure the controller's --navigation-peer with the upper computer's source IPv4 address as seen by the controller. The controller launcher accepts this as NAVIGATION_PEER; persist it in the service environment for deployment. The local browser bridge retains --control-peer 127.0.0.1.

The SDK's robot_ip is the controller's address. Installing the ROS package does not deploy or configure the controller update. The original loopback-only filter rejects remote motion commands, even if telemetry works.

Build

Place this repository at ~/rk3506_ros2_ws/src/rk3506-mobile-base-ros2-sdk, then build from the workspace:

mkdir -p ~/rk3506_ros2_ws/src
cd ~/rk3506_ros2_ws
source /opt/ros/humble/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --packages-select rk3506_driver
source install/setup.bash

For Jazzy on Ubuntu 24.04, source /opt/ros/jazzy/setup.bash instead. Use a separate workspace and terminal environment for each distribution. rosdep installs the dependencies declared in package.xml.

Configure and launch

Copy the supplied configuration outside the install tree:

cd ~/rk3506_ros2_ws
cp src/rk3506-mobile-base-ros2-sdk/rk3506_driver/config/driver.yaml ./rk3506-driver.yaml

Edit robot_ip to the controller's reachable IPv4 address. Review frames, velocity limits and timeouts, then launch:

source install/setup.bash
ros2 launch rk3506_driver driver.launch.py params_file:="$PWD/rk3506-driver.yaml"

The supplied address is 192.168.50.1. All driver parameters are read-only after startup; edit the YAML and restart the node to apply changes. The default node name is rk3506_driver. For a namespace:

ros2 launch rk3506_driver driver.launch.py \
  params_file:="$PWD/rk3506-driver.yaml" namespace:=robot1

The YAML uses /**, so it also applies to namespaced nodes. Interfaces in this example become /robot1/cmd_vel, /robot1/wheel/odometry, /robot1/stop, etc.

To run the executable directly with a topic remapping:

ros2 run rk3506_driver rk3506_driver_node --ros-args \
  --params-file "$PWD/rk3506-driver.yaml" -r cmd_vel:=/navigation/cmd_vel

Usage

Source the ROS environment and workspace in each command-line terminal. Once the supervised robot checklist permits motion, applications publish body velocity directly; the SDK manages sessions internally. There are no public acquire/release, motor-enable or fault-clear services.

With default Twist input, request a low forward speed at 20 Hz:

ros2 topic pub --rate 20 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.05, y: 0.0}, angular: {z: 0.0}}'

linear.x and linear.y are body-frame velocities in m/s; angular.z is yaw rate in rad/s. Stop the publisher with Ctrl+C. The configurable command timeout defaults to 300 ms and requests zero through the controller's deceleration logic; it is not a guarantee of physical stopping time.

For stamped input, set use_stamped_cmd_vel: true in the YAML and restart. The ROS CLI refreshes stamp: now for each publication:

ros2 topic pub --rate 20 /cmd_vel geometry_msgs/msg/TwistStamped \
  '{header: {stamp: now, frame_id: base_link}, twist: {linear: {x: 0.05}, angular: {z: 0.0}}}'

Use the configured base_frame or an empty frame ID. Keep the publisher and driver ROS clocks aligned. Exactly one input message type is active.

Read feedback in separate terminals as needed:

ros2 topic echo /wheel/odometry
ros2 topic echo /battery_state
ros2 topic echo /digital_inputs
ros2 topic echo /diagnostics

Request a software stop:

ros2 service call /stop std_srvs/srv/Trigger '{}'

success: true means the controller acknowledged the stop request. Rejection, another velocity owner, an unavailable controller or missing acknowledgement returns success: false with an explanation. This does not prove physical standstill.

Software stop is latched. Stop the velocity publisher and clear it explicitly through the existing web UI. DI1/DI2 retain motor-enable authority; the SDK never clears a stop or fault automatically.

Browser control and reconnection

Browser control takes priority. ROS messages during browser control are discarded; after browser release, the next new ROS velocity command resumes navigation automatically. A still-running ROS publisher can therefore resume immediately; stop it before releasing browser control when no further motion is intended.

Node startup alone does not request motion. After a detected communication loss, telemetry subscriptions recover automatically and cached velocity is discarded. Motion requires a fresh ROS command. The controller's independent watchdogs and physical motor interlocks remain active.

Interfaces

Names below are relative to the node namespace, except the standard /tf topic.

cmd_velgeometry_msgs/msg/TwistOptional TwistStamped via use_stamped_cmd_vel; one active type
wheel/odometrynav_msgs/msg/OdometryValid controller pose/twist only
battery_statesensor_msgs/msg/BatteryStateValid battery samples only

cmd_vel is subscribed; telemetry and TF are published; stop is a service. digital_inputs encodes DI1–DI8 in bits 0–7.

TwistStamped requires a current ROS-clock timestamp and an empty or configured body frame ID. Stamps older or further in the future than command_timeout are rejected. Planar commands must be finite, within configured limits, and have zero linear Z and angular X/Y. Invalid commands clear the SDK's desired velocity.

Covariance entries are ordered X, Y, Z, roll, pitch, yaw and must be finite and nonnegative. Defaults are uncalibrated. Frame IDs must be nonempty, distinct and have no leading slash. Timeouts and velocity limits must be finite and positive; velocity limits cannot exceed the protocol range of 32.767.

The editable template is driver.yaml.

Odometry and navigation integration

Wheel odometry comes from the controller; the SDK does not integrate motion a second time. Sensor fusion and localization remain on the upper computer.

TF is off by default. Enable publish_tf only when no other estimator publishes the configured odometry-to-body transform. Covariance defaults are uncalibrated and configurable. In the navigation stack, bypass the upstream velocity smoother and remap the collision-checked body velocity output to this node's cmd_vel; retain collision checking and keep smoothing on the Controller.

Telemetry uses ROS reception time. Missing or invalid measurements are withheld; diagnostics report failure/staleness. Cached battery/input packets cannot prove source sample age. Battery current follows the BMS signed current convention; temperature is the mean pack NTC temperature, while unavailable per-cell voltage and design capacity remain NaN. No source clock synchronization is claimed.

The wheel-odometry origin resets when the reader restarts. V1 neither stitches pose across restarts nor guarantees restart detection; recover the upper-level estimator after a known restart.

Diagnostics and troubleshooting

Diagnostics include controller flags, owner session, command age, sensor health, malformed-packet counts and receive age. They distinguish missing recent samples (STALE), failed samples or latched controller faults/stops (ERROR), and inhibited motion, another velocity owner or simulation (WARN).

SymptomCheck
Package not foundBuild the workspace and source install/setup.bash in the current terminal
No telemetry or stale diagnosticsCheck controller IP, UDP ports, routing, reply traffic and running controller services
Telemetry works but commands do notCheck the companion update, navigation-peer source IP, DI1/DI2 state, latched faults/stops and browser ownership
No matching cmd_vel subscriberCheck namespace, remapping and the selected Twist/TwistStamped type
Stamped commands rejectedCheck timestamp freshness, clock alignment and body frame ID
Parameter update rejectedEdit the YAML and restart; driver parameters are read-only
Duplicate odometry TFKeep one publisher for the configured odometry-to-body transform

colcon test --packages-select rk3506_driver --event-handlers console_direct+

The 13 integration cases start the real node with a simulated UDP peer on loopback and an isolated ROS domain. They cover forwarding, command expiry, handoff, reconnect, stop outcomes, telemetry, invalid input, stamped commands, optional TF and startup configuration. They do not contact a physical robot.

From the repository root, repeat isolated checks in existing ROS containers:

tools/validate-container.sh ros2-humble-dev humble
tools/validate-container.sh ros2-jazzy-dev jazzy

The script requires Docker and a running container with the selected ROS distribution and package dependencies installed. It creates a temporary workspace and a copied install, preserving other workspaces. Logs and XML results go to ignored artifacts/ directories.

RK3506 移动底盘 ROS 2 SDK

本 SDK 用于将 RK3506 禾利时双舵轮移动底盘接入 ROS 2。SDK 运行在上位机， 通过 UDP 与 RK3506 上独立运行的控制器通信。

C++ ROS 包名为 rk3506_driver。控制器程序位于独立的 rk3506-can-interface-cpp 仓库。已执行的检查及尚未完成的实车验收见 验证报告。

支持平台

ROS 2 发行版操作系统架构
HumbleUbuntu 22.04ARM64、x86_64
JazzyUbuntu 24.04ARM64、x86_64

四种组合均已通过构建和集成检查。ARM64 在原生架构 Docker 容器中验证， x86_64 使用仿真运行。实车验收尚未完成。

使用条件

  • 上位机已安装对应版本的 ROS 2、支持 C++17 的编译器、colcon，并完成 rosdep 配置。

  • 上位机能访问控制器的 UDP 端口：5003 用于底盘指令与状态，5001 用于 电池，5002 用于数字输入。网络也需要允许控制器向上位机返回 UDP 数据。

  • 控制器已安装配套的远程导航访问与浏览器控制权切换更新，详见 控制器集成说明。

控制器的 --navigation-peer 应设置为控制器实际看到的上位机源 IPv4 地址。 控制器启动脚本通过 NAVIGATION_PEER 接收此设置，部署时应写入服务环境以便 重启后保留。本地浏览器桥接程序继续使用 --control-peer 127.0.0.1。

SDK 的 robot_ip 则是控制器的地址。安装 ROS 包不会自动部署或配置控制器 更新。原先仅允许回环地址控制的版本，即使可以接收遥测，也会拒绝远程运动指令。

构建

将本仓库放在 ~/rk3506_ros2_ws/src/rk3506-mobile-base-ros2-sdk， 然后在工作空间根目录构建：

mkdir -p ~/rk3506_ros2_ws/src
cd ~/rk3506_ros2_ws
source /opt/ros/humble/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --packages-select rk3506_driver
source install/setup.bash

在 Ubuntu 24.04 上使用 Jazzy 时，将环境文件改为 /opt/ros/jazzy/setup.bash。 不同发行版应使用各自的工作空间与终端环境。rosdep 根据 package.xml 安装依赖。

配置与启动

将提供的配置模板复制到安装目录之外，便于维护：

cd ~/rk3506_ros2_ws
cp src/rk3506-mobile-base-ros2-sdk/rk3506_driver/config/driver.yaml ./rk3506-driver.yaml

将 robot_ip 改为可访问的控制器 IPv4 地址，检查坐标系、速度上限和超时时间， 然后启动：

source install/setup.bash
ros2 launch rk3506_driver driver.launch.py params_file:="$PWD/rk3506-driver.yaml"

模板默认地址为 192.168.50.1。驱动参数在启动后均为只读；修改 YAML 后需要 重启节点才能生效。节点默认名称为 rk3506_driver。指定命名空间的示例：

ros2 launch rk3506_driver driver.launch.py \
  params_file:="$PWD/rk3506-driver.yaml" namespace:=robot1

YAML 使用 /**，因此也适用于带命名空间的节点。上述接口名称将变为 /robot1/cmd_vel、/robot1/wheel/odometry、/robot1/stop 等。

也可以直接运行节点并重映射话题：

ros2 run rk3506_driver rk3506_driver_node --ros-args \
  --params-file "$PWD/rk3506-driver.yaml" -r cmd_vel:=/navigation/cmd_vel

使用方法

每个命令行终端都需要加载 ROS 环境和工作空间环境。完成现场监督下的 实车检查清单、确认允许运动后，应用直接发布底盘速度 即可，SDK 在内部管理控制会话。SDK 不提供显式申请/释放控制权、电机使能或 故障清除服务。

默认使用 Twist 输入。以下示例以 20 Hz 请求低速前进：

ros2 topic pub --rate 20 /cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 0.05, y: 0.0}, angular: {z: 0.0}}'

linear.x 和 linear.y 是车体坐标系下的线速度，单位 m/s；angular.z 是 偏航角速度，单位 rad/s。按 Ctrl+C 停止发布。指令超时默认为 300 ms，可通过 参数配置；超时后 SDK 请求零速度，由控制器执行减速。这不是实车停止时间保证。

如需带时间戳的输入，在 YAML 中设置 use_stamped_cmd_vel: true 并重启。 ROS CLI 会在每次发布时刷新 stamp: now：

ros2 topic pub --rate 20 /cmd_vel geometry_msgs/msg/TwistStamped \
  '{header: {stamp: now, frame_id: base_link}, twist: {linear: {x: 0.05}, angular: {z: 0.0}}}'

坐标系填写配置的 base_frame，也可以留空。发布端与驱动应使用对齐的 ROS 时钟。任一时刻只启用一种输入消息类型。

按需在不同终端查看反馈：

ros2 topic echo /wheel/odometry
ros2 topic echo /battery_state
ros2 topic echo /digital_inputs
ros2 topic echo /diagnostics

请求软件停止：

ros2 service call /stop std_srvs/srv/Trigger '{}'

success: true 表示控制器已确认停止请求。如果请求被拒绝、控制权属于其他 来源、控制器不可用或未收到确认，则返回 success: false 及原因说明。 该返回值不能证明机器人已在物理上完全停止。

软件停止会锁存。先停止速度发布，再通过现有 Web 界面显式清除。 DI1/DI2 始终保留电机使能权限，SDK 不会自动清除停止或故障状态。

浏览器控制与重连

浏览器控制优先。浏览器持有控制权期间收到的 ROS 指令会被丢弃。 浏览器释放控制权后，只有新收到的 ROS 速度指令才能自动恢复导航。 因此，如果 ROS 发布器仍在运行，导航可能立即恢复；如果不希望继续运动， 请先停止发布器，再释放浏览器控制权。

节点启动本身不会请求运动。检测到通信中断后，SDK 会自动恢复遥测订阅， 并丢弃缓存速度；恢复运动需要新的 ROS 指令。控制器自身的看门狗和物理 电机联锁始终有效。

里程计与导航集成

轮式里程计来自控制器，SDK 不会再次积分运动。传感器融合和定位在上位机完成。

TF 默认关闭。仅在没有其他估计器发布对应里程计到车体坐标变换时，才启用 publish_tf。协方差默认值未经标定，可按实际情况配置。接入导航栈时， 绕过上游速度平滑器，将经过碰撞检查的车体速度输出重映射到本节点的 cmd_vel；保留碰撞检查，由控制器统一负责速度平滑。

遥测使用 ROS 接收时间。缺失或无效测量不会发布，诊断会报告失败或超时。 缓存的电池或输入数据不能证明源测量的采集时间。电池电流沿用 BMS 的有符号 电流约定，温度为电池包 NTC 温度均值；无法获得的单体电压及设计容量使用 NaN。不提供源时钟同步保证。

控制器采集进程重启后，轮式里程计原点会重置。V1 不拼接重启前后的位姿， 也不保证检测到每次重启。确认采集进程重启后，应恢复上位机估计器。

诊断与故障排查

诊断包含控制器标志位、控制会话、指令年龄、传感器健康状态、异常报文计数 及接收数据年龄。近期未收到数据为 STALE；测量失败或控制器故障/软件停止 锁存为 ERROR；运动受限、控制权属于其他来源或使用仿真控制器为 WARN。

现象检查项
找不到 ROS 包构建工作空间，并在当前终端加载 install/setup.bash
没有遥测或诊断显示过期检查控制器 IP、UDP 端口、路由、返回流量及控制器服务
有遥测但运动指令无效检查配套控制器更新、导航来源 IP、DI1/DI2、锁存故障/停止及浏览器控制权
cmd_vel 没有匹配的订阅者检查命名空间、重映射及 Twist/TwistStamped 类型选择
带时间戳指令被拒绝检查时间戳、时钟对齐及车体坐标系
参数修改被拒绝参数为只读，编辑 YAML 后重启节点
里程计 TF 重复对同一里程计到车体坐标变换只保留一个发布者
